# IDD-0007.spec-mvp-operability-and-quality

## Intent

The browser application stays usable while parsing meshes and performing
potentially expensive geometry operations. Large or invalid input produces
progress and actionable limits rather than a frozen page. The workspace itself
remains usable at supported desktop and narrow viewport sizes without layout
overflow hiding essential controls or preview content.

## Behavior

- User-visible processing stages distinguish template import, SVG import,
  placement/topology, bridge generation, solid boolean generation, preview
  update, and export preparation.
- Processing state is visible in a compact status treatment; detailed status
  text must not reserve a large permanent section of the workspace.
- CPU-heavy geometry work runs away from the main UI event loop so orbiting the
  view, progress display, and cancellation/stale-result handling remain
  responsive.
- Rapid edits are debounced or coalesced. Older in-flight geometry results are
  discarded when newer design state exists.
- Template and SVG size/complexity limits are explicit and configurable.
  Exceeding a limit produces a clear error before uncontrolled memory or CPU
  growth.
- Invalid STL/3MF topology, unsupported SVG content, boolean failures, and
  export failures have distinct user-facing messages.
- On wider screens the primary settings area may scroll independently when its
  content exceeds the available height. That content must not force the compact
  preview to grow to the same height.
- On narrow screens (at or below 900 CSS pixels), settings, export actions, and
  the compact preview appear in that order in one vertically scrollable document.
  Neither the settings area nor the preview uses a separate document-height
  scroll region, and the export panel does not stick over other controls.
- Project file selection is presented as two compact status cards with a
  keyboard-accessible action each. Long names truncate visually within their
  cards rather than forcing native file-picker controls to overflow; the
  complete name is available as text/tooltip.
- Supported viewport sizes do not produce document-level horizontal overflow;
  controls, canvas content, and action areas remain within the browser width.
- On narrower layouts the workspace stacks, the preview remains bounded below
  the settings, and its expand action remains available. The expanded preview
  may temporarily lock page scrolling; closing it must restore normal scrolling
  without resetting the page position.
- Inputs are deterministic: identical template bytes, artwork, placement,
  bridge settings, caption settings, and colors produce geometrically
  equivalent output.
- The application does not require cross-origin APIs, a backend, or a service
  worker to perform its core generation workflow.
- Production builds are tested before GitHub Pages deployment.

## Product-Significant Architecture And Constraints

- The application must remain deployable as ordinary static files on GitHub
  Pages.
- Heavy work may use Web Workers and WebAssembly libraries, but must not require
  a server-side companion.
- Temporary geometry created for failed or superseded operations is releasable
  so repeated edits do not cause unbounded memory growth.
- Accordion state, scroll position, and compact/expanded preview state are UI
  concerns and do not belong in `ProjectSettings`.

## Non-goals

- Instantaneous recomputation for arbitrarily large professional CAD meshes is
  not promised.
- Automatic repair of every malformed STL/3MF file is not required.

## Acceptance Criteria

- A typical coffee-stencil template and SVG can be edited without multi-second
  main-thread freezes.
- A complex but permitted operation shows progress and either completes,
  reports a specific error, or is safely superseded by a newer edit.
- Repeated edits do not apply out-of-order results.
- Invalid input never leaves controls permanently disabled.
- At typical desktop zoom the primary controls and complete compact preview can
  be used without horizontal document scrolling.
- Narrow supported viewports reflow without controls or canvas increasing the
  document width beyond the viewport.
- Mobile file cards keep readable names and upload/replacement actions without
  clipped native file-input text at 375, 390, or 430 CSS pixels.
- At mobile and narrow viewport widths, the document has a single vertical
  scrollbar; the settings are reachable without the preview persistently
  occupying the visible screen area, and export stays in normal flow.
- Opening and closing the expanded preview preserves the viewport camera and
  normal page scroll position.
- A production build works from the configured GitHub Pages project subpath.

## Verification

- Stress template import, SVG import, repeated placement changes, boolean
  generation, and both export paths.
- Verify stale worker results cannot overwrite newer state.
- Verify explicit failure cases for invalid meshes, unsafe SVG, complexity
  limits, boolean failure, and 3MF/STL serialization.
- Check desktop viewport sizes at 100% browser zoom for independent settings
  scrolling and bounded preview sizing.
- Check 375, 390, 430, 768, and 900 CSS-pixel widths for one document scrollbar,
  controls followed by export and preview, no sticky export region or horizontal
  overflow, and opening/closing expanded preview without losing scroll position.
- Check a wider desktop viewport for the original side-by-side layout.
